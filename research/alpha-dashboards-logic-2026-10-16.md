## 0. 先看整体：作者怎么用这些指标

1. **只用相对标尺。** 三页的阈值都是当前窗口内的分位数，没有任何固定数值阈值：
   - 链上页取近 30 天的 P75 和 P95；
   - 永续页取 90 天参考窗内的 P75 和 P90。

   所以标签的意思是"在最近这段时间里算大"，不能拿来和别的时期直接比。
2. **先去掉噪音再看短期持有者。** STH 都会剔除持有不足 1 小时的币，state-report 还可以选择再剔除 1 小时到 1 天的币。这些短线快进快出的币不算真正的卖方。剔除确实影响结果：近 30 天里，<1h 的币约占 STH 亏损的 13%；不剔除的话，图 1 的 P95 会从 $41.3M 升到 $43.8M（复算）。
3. **累计值做差分，只取正数。** BRK 提供的是创世以来的累计值，每小时值 = max(0, 本小时累计 − 上小时累计)。
4. **不做综合信号。** 没有评分，也没有"多图同时超阈值就报警"的逻辑。阈值只用于画虚线和图例。结论由人来写：state-report 的 "Analyst Take" 和 onchain-seller 的解读区块都是空槽位，作者指南写明每期人工撰写，不超过 250 词。
5. **页头用同一套周期六态。** 两个 alpha-vol 页都显示周期状态，例如 "Breakout since …"。算法与 alphabtc 的 classifier v2 同源，但门控方式不同，见 §3.3。
6. **只加载一次，不轮询。** 打开页面时取一次数据，之后不再刷新。最后一根未收盘的 bar 照常参与计算、作图和求阈值，页头 "Data" 显示的就是这根 bar 的起始时间。只要有一个请求失败，整页报错，不会显示旧数据，也不会补 0。

## 1. onchain-seller（On-chain Local Last Seller）

它回答的问题是：**最近的卖压是不是新进场的人在亏本割肉？**

### 1.1 计算

- **小时数据的取舍**：价格和 4 条累计值的当前值与前值都不为空时，才保留这一行。
  - BRK 在没有出块的小时只返回时间戳，代码会丢掉这一行，并连带丢掉下一行。2600 小时里有 11 个这种小时。
  - 结果按 $100 取整后存储。
- **三张图（SOP Flow tab）**：都是 1 小时一根柱，不做平滑。下式中 `x1` 表示 STH 已剔除 <1h 的币。

| 图 | 公式 |
|---|---|
| 1 已实现亏损（堆叠） | LTH_loss + STH_loss_x1。其中 STH_loss_x1 = max(0, ΔSTH_loss − Δ<1h_loss)；<1h 数据缺失时，这一小时不剔除 |
| 2 STH 亏损占卖方比例 | STH_loss_x1 ÷ (LTH_profit + LTH_loss + STH_profit_x1 + STH_loss_x1)。分母 ≤ 0 时整行跳过；没有分母下限，近 30 天分母最小约 $0.98M，中位数约 $20.9M |
| 3 STH 亏损供应占比 | (STH_in_loss − <1h_in_loss) ÷ (同口径的 in_loss + in_profit) |

- **阈值的算法**：
  - 窗口是最后一根 bar 往前 720 个小时，包含未收盘 bar。
  - 分位数用 `d3.quantileSorted`，即 R-7 线性插值。
  - 每次加载只算出一组值，画成横贯整个 Span 的虚线。也就是说，历史上每根柱都是和"今天的 30 天阈值"比较，阈值并不随时间滚动。
  - 切换 Span（7d/30d/90d，即最后 168/720/2160 根）不改变阈值。

### 1.2 读法（页面说明加源码）

- **图 1**：看规模和谁在卖。红色虚线是 P95，黄色是 P75。关注成串的高柱，单根高柱意义不大。
- **图 2**：看是不是最新进场的人在认输。它是比例，行情清淡时也可能偏高，所以必须配合图 1 的规模一起看。
- **图 3**：看水下的存量有多少。它是存量：价格跌破近期买家成本时上升，涨回成本以上时下降。图 1 里 STH 的亏损柱，就是从这个存量里流出的。

## 2. perp-squeeze（Perp Squeeze Indicator）

它回答的问题是：**这段价格是杠杆推动的（被迫平仓或新开仓），还是现货推动的？**

### 2.1 数据与 block

- **数据结构**：`rows` 里含共用的 price，以及按交易所（all、binance、bybit、hyperliquid）分组的 oi_btc、vd_btc、funding、long_liq_btc、short_liq_btc。所选交易所没有数据时，回落到 all。
- **Hyperliquid 的清算**：在每个 10m 桶里按 OI 占比估算，即 aggregated 清算 × HL_OI ÷ all_OI。界面不会标注"估算"。因为是按比例缩放，HL 的多空清算比与 aggregated 几乎相同，HL 的 squeeze 实际反映的是 CEX 的清算（推断）。
- **Block 切分**：按 UTC epoch 对齐。4h 为每 24 个 10m 桶一块，8h 为每 48 个。
  - 末尾不足半块的直接丢弃。
  - 超过半块但未完成的块会参与分类。
- **每块的 4 个量**：

| 量 | 算法 |
|---|---|
| dPx | (末桶价 ÷ 首桶价 − 1) × 100，带符号。首桶取的是收盘价，所以会漏掉块内最初的 10 分钟（推断） |
| dOI | 末桶 OI − 首桶 OI，单位 BTC |
| delta | 块内 vd 求和 |
| 多 / 空清算 | 块内分别求和 |

- **缺失值**：分类时 null 当 0 处理。首尾价格或 OI 无效时，对应的 dPx 或 dOI 记为 0，这些 0 也会进入分位数分布。

### 2.2 阈值与 8 种状态

- **参考窗口**：取到的全部块，约 90 天加今天，4h 下约 542 块，包含最新块。
- **分位数**：取排序后第 floor(q·(n−1)) 个值，不插值；判定一律用 `≥`。
- **4 个阈值**：

| 记号 | 定义 |
|---|---|
| T_sLiq | 空头清算的 P90 |
| T_lLiq | 多头清算的 P90 |
| T_oi | \|dOI\| 的 P75 |
| T_px | \|dPx\| 的 P75 |

- **判定**：按下面的顺序，取第一个满足的状态。

```text
short squeeze : sLiq ≥ T_sLiq  且 dPx ≥  T_px 且 sLiq ≥ 3·lLiq
long squeeze  : lLiq ≥ T_lLiq  且 dPx ≤ −T_px 且 lLiq ≥ 3·sLiq
unwind        : dOI ≤ −T_oi → delta < 0 为 long unwind，否则为 short unwind
new long      : dOI ≥  T_oi 且 dPx > 0 且 delta > 0
new short     : dOI ≥  T_oi 且 dPx < 0 且 delta < 0
spot-led      : |dPx| ≥ T_px 且 |dOI| < T_oi
chop          : 其余全部（包括 OI 大升但价格和 delta 方向不一致的情况）
```

- **为什么 squeeze 要三个条件同时成立**：源码注释记录了一次修正。早期只看"清算进入前 10% 且价格方向一致"，结果 163 小时里有 28 小时被标成 squeeze，其中一小时只清算了 40 BTC、价格只动了 0.08%。原因是这条序列大部分时间是 0，前 10% 并不代表量大。
- **阈值的修订**：2026-10-01 起，OI 和价格都改为 P75。此前 OI 是 P60、价格是 P70，源码注释说当时的不对称没有记录理由。
- **边界情形**：两侧清算都为 0 时，`0 ≥ 3·0` 成立。但还要求清算 ≥ P90，所以只有 P90 本身为 0 时才会被误判成 squeeze。如果整列清算数据缺失，所有价格大幅变动的块都会被标成 squeeze。
- **funding 未使用**：代码算了每块的平均 funding，之后再也没有读取它。

### 2.3 表与图

- **Prob.**：中点落在 Show 区间内的块中，各状态的占比。用最大余数法取整，保证合计 100%。
- **Max DD**：把相邻的同状态块合并成一段，取"首块首桶到末块末桶"收益绝对值最大的那一段，保留正负号。时长 = 块数 × 块长。它衡量的是这段的最大涨跌幅，不是回撤。
- **最新块的圆点**：标的是最后一块。当前块已过半时，标的是这根未收盘的块。
- **图 1、图 2**：在价格线上，按块的状态着色。
- **图 3**：所选交易所的 OI 和价格，各取块收盘值。
- **图 4**：每块的 delta 和清算合计。页面写 "per bucket"，实际是每个 block。
- **"Resolution 10m"**：指取数和计算的粒度，是 HTML 里写死的文字。
- **切换 Exchange**：OI、vd、清算换成该交易所的序列，4 个阈值、全部状态、表和图都会重算。价格和页头不变。
- **Parameters 小标题**：说"阈值打印在 Parameters 下"，但那一行已经删除，界面上看不到阈值数值。

### 2.4 读法要点

- **标签会随时间变动。** 每块都是和整个参考窗口比，阈值里包含了这块之后的数据。窗口一滚动，旧块的标签就可能改变，所以不能把历史标签直接当作回测样本（推断）。
- **清算是交易所上报的数，只能当下限。** 一次被迫平仓有可能被标成 unwind。
- **builds 会累积以后可能被强平的仓位；spot-led 的行情这类风险较小**（页面说明）。

## 3. state-report（BTC 周期择时系统 · 链上报告）

它回答的问题是：**谁在卖（新币还是老币）、在哪些成本价上换手、成本密集带在哪里？**

### 3.1 通用

- **请求数**：628 次，其中 series 209、URPD 53、URPD dates 1、图 8 的日快照 365。
- **每小时值**：用累计值做差分，结果 clamp 到 ≥ 0；有任一值缺失，整小时丢弃。
- **Smoothing（1h/24h/168h）**：尾随简单均值，窗口包含当前小时，分母固定为 w，不足 w 行的开头几行丢弃。窗口按行数计，不按时间计。每个分项先平滑，再算占比。
- **Span**：只决定显示最后 24、168、720 或 2160 行。

### 3.2 各图规则

| 图 | 规则 |
|---|---|
| 1 A/B 卖方构成 | Measure 有三种：P&L $ 用 `realized_{profit,loss}`；Spent BTC 用 `transfer_volume_in_{profit,loss}`；Spent $ 用后者的 `_usd` 版本。A 图是各分项 ÷ 可见分项之和，B 图是绝对值堆叠。<br>Exclude 只作用于 STH 的两腿：<1h 扣掉 `utxos_under_1h_old`，<24h 再扣 `utxos_1h_to_1d_old`；扣之前每项先 clamp 到 ≥0，扣完的残差也 clamp 到 ≥0 |
| 2 全年龄段 | 23 个 cohort 先并成 12 档，再并成 6 档：<1w、1w–1m、1m–6m、6m–2y、2y–5y、5y+。profit 向上堆，loss 向下堆。不做 <24h 剔除 |
| 3 按成本价看买卖 | 每个价格桶算"今天快照 − 窗口起点快照"。STH 用 lin200，All 和 LTH 用 lin500。<br>今天的快照是实时状态，过去日期是日终状态，所以 "1d" 窗口实际只覆盖约 8–10 小时（复算）。<br>AGING=Show 时，卖方另画一条 −lth_d 的空心"老化下界"：这部分减少只是币老化成了 LTH，不是真的卖出 |
| 3 中的 K1–Kn | 不是 k-means。做法：先做加权高斯 KDE，带宽 = bw × 可见价格跨度；取局部极大，保留 prominence ≥ 最高峰 5% 的峰，峰数没有上限。<br>表格各列：WIDTH = 半高全宽（FWHM）；BTC = 中心 ±FWHM/2 内的权重和；SHARE = BTC ÷ 该侧总权重；STRENGTH = prominence ÷ 最高峰 |
| 3 中的 Bell curves | 加权一维高斯混合（GMM），用 EM 拟合，最多 120 次迭代。<br>"auto" 时成分数 = KDE 峰数，上限 min(5, 桶数/5)。只有 Smoothing=Off 时才用 BIC 选成分数，但 logL 被按权重归一化了，实测 BIC 恒选 k=1（复算） |
| 4 年龄拆分 | bought = 今天快照里币龄小于窗口长度的币，按年龄精确拆分。<br>sold = 起点快照 − (今天快照 − bought)。卖方的币龄是推断：用 5600 天的日线高低价，从新往旧扫，记下每个 $500 桶最后一次被价格覆盖的日期，以此作为这些币的最小币龄 |
| 5/6 钱包规模 | Δ = 最新 hour1 − n 小时前，不平滑。<br>Entities 分组：Retail = <1 BTC 的 6 档，Small = 1–100 BTC，Mid = 100–10k BTC，Large = ≥10k BTC。<br>"% of band" 除以组内当前 supply 之和；"% of realized cap" 除以组内当前 realized_cap 之和 |
| 7 存量成本分布 | K = KDE 峰，M = GMM 成分，右侧 rail 上的 ±σ 是 μ±1σ。<br>四条参考线 True mean、Short-term、Average、Long-term 固定取最新值，不随 Snapshot 切换。<br>Median 用 all lin500 计算，在桶内线性插值。in profit = 桶中心 ≤ 快照收盘价的 supply ÷ 桶中心 ≥ $1000 的总 supply |
| 表 2 价位 | 把可见价格域切成 $2,000 一段。段内有任一参考价位就算"有效段"，参考价位包括 5 条模型线和各 M 成分的 μ−σ、μ、μ+σ。排除现价所在段，上下各取最近 4 段：阻力取段上沿，支撑取段下沿。<br>列名"1-Week…4-Week"只是序号，没有时间含义 |
| 8 成本热力图 | CONTRAST 默认是 P75–P95，在可见格子上按最近秩取分位，≤ P75 的格子画成和空格一样的底色，色阶 4 级。<br>只保留 floor ≥ $1000 的桶。"All" 实际是最近 1461 天 |

### 3.3 页头周期状态（两个 alpha-vol 页共用）

**三个量**
- depth = 100·ln(W/TMM)
- spread = 100·ln(STH/TMM)
- pvs = depth − spread

其中 W 是 1 天–1 周持有者成本，TMM 是 true market mean，STH 是短期持有者成本。三个量的正负号对应三条成本线的 6 种排序，即 6 个状态。

**两版实现的差异**

| | alpha-vol 页头 | classifier v2（alphabtc） |
|---|---|---|
| 起算日 | 2013-01-01 | 2015-01-01 |
| 死区 depth / pvs / spread | 7.0 / 6.8 / 1.25 | 6.95 / 6.65 / 1.40 |
| 滞回方式 | 整体门控：所有翻转的分量都越过死区才切换 | 每个分量独立滞回 |
| 初始状态 | — | 首个有效日取 `≥ 0` |

**复算**
- 两种算法都得到 Breakout since 2026-09-23 · day 24，与页面一致。
- W > TMM > STH 的排序自 08-26 起就成立，但 depth 要超过 7 才切换：09-22 为 4.41，09-23 为 7.46。
- 2015 年以来，两种算法有 23 天的标签不同，共 7 段。差异来自门控方式和起始日，不是阈值。

| Exp4 Realized Cap Change | 滚动窗口 w 内的变化：(cap[i] ÷ cap[i−w] − 1) × 100。7D 为 +0.11%（复算） |
| Exp5 Realized P/L Ratio | 先算每日 profit/loss 比，再取简单移动平均；窗口内必须每天都有值。7D 为 2.02（复算） |
| Exp6 Supply in Profit | 各 cohort 的盈利供应占比。<1M…<6M 组用 盈利供应 ÷ 供应 自算，其余直接取 BRK。STH 当前为 68.32%（复算） |

- **联动**：Exp3 选的比较指标，与 Exp4/5/6 的分组是同一个设置；Exp4/5/6 的跨度和窗口也互相联动。
- **综合结论**：同样没有打分或买卖信号。唯一的标签是周期状态，用于 Exp1 着色、Exp3 分段，并在 Exp3 的状态按钮上标出今天的状态。`.read` 解读块和页头摘要都是留给人工填写的空槽位。

**核验**：源码注释里的 8 个静态数字，7 个复算一致：48 次切换；2019、2023 年 Repair 分别持续 41、218 天；2026 年 Repair 于 09-22 结束；Exp5 在 10-14 的 30D 均值 4.4；<5M 组与 STH 盈利占比之差 ≤ 0.0001；log200 共 718 桶；LTH-USD 档共 21 个分位。唯一不一致的是注释写 10-14 的 24h P/L 比为 0.77，复算为 0.81，推断作者是在当天未收盘时记的数。

**读法提醒**
- Exp3 的顶部线是历史上同一状态各段的高位读数，包含该状态结束之后的走势。例如 2019 年的 Repair 段只有 41 天，它的顶部其实来自之后的行情。这条线是历史类比，不是目标价。
- Exp5 是"比值的平均"，不是"总额之比"。两者可能差很多：10-14 的 30D 均值为 4.38，同期总额之比只有 2.53。
